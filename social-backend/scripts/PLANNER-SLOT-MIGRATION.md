# Planner reservation rollout

No live migration has been performed by this change. The normal index bootstrap does not remove legacy indexes; it warns and leaves an old unique account/instant index unchanged.

## Explicit operator workflow

1. Back up the database and deploy matching planner API and worker code in a coordinated maintenance window. Stop API writers, maintenance recovery, schedulers and publishing/retry workers before applying the index change. Do not mix old and new scheduling writers after migration.
2. From the backend root, run `python -m app.core.planner_slot_migration` for a read-only preflight. It reports reservation count, legacy unique index names and errors. It does not initialize indexes or change documents.
3. If preflight reports missing workspace/post IDs, duplicate workspace/post reservations or incompatible named indexes, stop and reconcile manually with the backup and post history. The migration deliberately does not delete or merge reservations.
4. Only after all writers are stopped, run `python -m app.core.planner_slot_migration --apply --writers-stopped`. This explicitly acknowledges the maintenance requirement; the flag does not stop processes for the operator.
5. Verify the resulting indexes: `planner_workspace_post_unique` is unique on workspace/post; `planner_account_instant_lookup` is nonunique on workspace/account/instant. Legacy unique account/instant indexes, detected by their key fields rather than a hard-coded name, must be absent. Reservation documents and their IDs remain unchanged.
6. Resume matching API and workers, then verify read-only run access and scheduling previews before authorizing any actual scheduling/publishing. Existing per-post revision, edit lease and schedule-token fences remain required.

The unique per-post index is created before the old exclusive index is removed. If preflight or index creation fails, old exclusivity remains. A later interrupted index removal is resumable using the same migration. Never automatically recreate account/instant uniqueness as a rollback: legitimate distinct posts may now share an instant, and that rollback requires its own audited preflight.

## Additive API contract

All existing routes remain under `/api/v1/workspaces/{workspaceId}/social/content-plan`.

- `PlannerSelection`, `RunCreate`, `SlotEdit`, `ScheduleSelection` and `ScheduleConfirm` accept optional `conflictAcknowledgments: [{slotId, warningFingerprint}]`, defaulting to an empty list. Acknowledgments use the aggregate slot/outcome fingerprint, not a single warning's fingerprint. IDs and fingerprints are opaque.
- `PlannerSlot` and `ScheduleOutcome` add `warnings`, `warningFingerprint` (nullable) and `acknowledgmentRequired`. Schedule outcomes also expose `slotId`. Warnings do not enter `reasons` and do not make an otherwise valid item blocked. `canSchedule` describes readiness, not permission to skip warning consent.
- Each warning has `code: scheduled_post_conflict`, `postId`, `accountId`, `accountName`, `status`, `scheduledAt` (UTC), `localDate`, `localTime`, `timezone`, `utcOffsetMinutes`, a whitespace-normalized excerpt of at most 160 characters, and `fingerprint`. Only workspace-scoped scheduled/publishing posts with the same account and exact instant are included. The current post is excluded; drafts and stale/orphan reservations alone do not occupy a slot.
- Preview slots first. If the user chooses Continue anyway, send the matching aggregate acknowledgment on create. Adding acknowledgments alone does not change `previewToken`; selection/conflict changes do. Creation or editing without current consent returns HTTP 409 with `detail: {code: conflict_acknowledgment_required, slot: PlannerSlot}`. The slot includes the warnings needed to review and retry. Existing preview-token checks still apply to run creation.
- Slot editing retains the original `slotId`; the fingerprint also binds workspace, selected local date, account, platform, exact UTC instant, timezone and the warning snapshot. Changing selection invalidates old consent. Time-only editing does not revoke copy approval.
- Final scheduling always uses a fresh schedule preview. Preview may accept the same acknowledgment array to indicate current reviewed warnings, but clients must explicitly echo the acknowledgment array on confirmation as well. Earlier generation/edit acknowledgment is never final schedule consent. A changed conflict fingerprint, including conflicts appearing/disappearing after preview, returns a per-item blocked outcome with reason `conflict_snapshot_changed_preview_again`; obtain a new preview and ask again. Missing final consent returns a per-item blocked outcome with reason `conflict_acknowledgment_required`. No auto-shift, overwrite or paid retry occurs.
- Confirmation remains HTTP 200 with per-item outcomes and durable request-id idempotency. A stored result is returned unchanged for a repeated request ID. After a stored blocked result, use a new request ID following review/correction; a new preview is mandatory if the snapshot changed. Preview expiry, revisions, roles, approval, blackout and edit-lock guards remain.
- Successful generation/edit consent stores actor/time and slot snapshot separately from final scheduling consent. Successful scheduling stores `planner_conflict_acknowledgment` on the post with actor/time, preview ID and the acknowledged slot snapshot. This does not substitute for editorial/team approval or publishing tokens.
- Dates before workspace-local today are invalid (`past_date`), and instants at/before server now remain invalid (`past_slot`). Preview returns blocked rows so clients can correct/exclude them; create/edit/confirm cannot schedule them. Today is permitted only with a future instant. No date is silently advanced. Existing historical runs remain readable. DST ambiguity/gap and blackout validation are unchanged.
- Active reservation-owner edit leases remain `slot_edit_locked` blockers. Concurrent planner confirmations for the same account/instant are serialized with a fenced short lease; a busy slot requires re-preview. The application cannot provide a cross-collection transaction or exactly-once external publication guarantee, and unrelated legacy writers must not be mixed into deployment.
- If old exclusive indexes remain, a reservation collision returns `planner_slot_index_migration_required`, not a destructive write or generic duplicate-key failure. Operators must complete the explicit migration before enabling simultaneous-post scheduling.

## Image-agent handoff

The existing synchronous `image` and `image_locked` implementations, creative pipeline, image action schema and image routes are untouched. No delegation to a new image module was added. Integrators can later delegate those methods without replacing the scheduling/date changes in `content_plan_runs.py` or the new fields in `planner_schemas.py`. Preserve `serialize_item` warning annotation and all scheduling locks/token/revision checks when integrating visual operation DTOs.
